# 黒板スキーマ定義(STEP 1 成果物)

## 目的

黒板は「解の現在状態」を保持する共有データ構造。ドメイン(お題)に依存しない
汎用フォーマットとして設計し、株購入予想以外のお題にも流用できるようにする。

## スキーマ

```json
{
  "session_id": "2026-09-06_stock-outlook-001",
  "goal": "ある銘柄について、買い時かどうかを複数の専門家の視点で議論する",
  "created_at": "2026-09-06T10:00:00+09:00",
  "updated_at": "2026-09-06T10:15:00+09:00",
  "status": "in_progress",

  "facts": [
    {
      "id": "f1",
      "content": "直近の決算で売上が前年比+12%",
      "source": "human | ファンダメンタルズ専門家",
      "added_at": "2026-09-06T10:02:00+09:00",
      "sources": ["https://example.com/ir/q2"]
    }
  ],

  "proposals": [
    {
      "id": "p1",
      "author": "テクニカル専門家",
      "content": "移動平均線が上向きのため短期的には強気",
      "confidence": 7,
      "added_at": "2026-09-06T10:05:00+09:00",
      "responds_to": null,
      "sources": ["https://example.com/chart"]
    },
    {
      "id": "p2",
      "author": "反証専門家",
      "content": "p1は短期指標のみに依拠しており、マクロ環境の悪化リスクを考慮していない",
      "confidence": 6,
      "added_at": "2026-09-06T10:08:00+09:00",
      "responds_to": "p1"
    }
  ],

  "open_questions": [
    {
      "id": "q1",
      "content": "今期のセクター全体の資金流入は増加傾向か",
      "raised_by": "マクロ・センチメント専門家",
      "resolved": false
    }
  ],

  "history": [
    {
      "turn": 1,
      "actor": "テクニカル専門家",
      "action": "proposal_added",
      "ref_id": "p1",
      "timestamp": "2026-09-06T10:05:00+09:00"
    }
  ]
}
```

## フィールド解説

| フィールド | 役割 | 誰が書き込むか |
|---|---|---|
| `goal` | 議論のお題。セッション開始時に人間が設定 | 人間(初期化時のみ) |
| `facts` | 確定した客観的情報 | 人間 or 専門家(データに基づく発言時) |
| `proposals` | 各専門家の見解・提案。`responds_to`で他提案への反論を表現できる | 専門家のみ |
| `open_questions` | まだ答えが出ていない論点。これが0件かつ全専門家が低スコアになったら終了 | 専門家 or 人間 |
| `history` | 誰が何をした記録。監査ログ兼、要約生成時の参照元 | コントローラーが自動記録 |
| `sources` | `facts` / `proposals` の任意フィールド。Web 調査で参照した URL / 資料名の配列(STEP 6) | 調査ツールを持つ専門家 |

## 永続化方式

- 保存先: `blackboard-data/session-<session_id>.json`
- 書き込みタイミング: `facts` / `proposals` / `open_questions` のいずれかが更新されるたび、
  ファイル全体を上書き保存する(小規模なJSONのため差分更新はせず単純化する)
- 排他制御: 今回はコントローラー1プロセスのみが書き込む前提のため、ファイルロックは省略する。
  将来複数プロセス化する場合はここに排他制御を追加する

## 専門家に渡す「要約」フォーマット

黒板の生データをそのまま渡すとトークン消費が大きくなるため、自己採点の問い合わせ時には
以下の要約形式に変換して渡す。

```
お題: {goal}
確定している事実(直近5件): {facts の要約}
これまでの提案(直近5件、著者名付き): {proposals の要約}
未解決の論点: {open_questions の一覧}
```

`facts` / `proposals` が増えてきた場合は直近N件のみを渡す形にし、全文を毎回渡さないことで
トークンコストの増大を防ぐ(件数の閾値はSTEP 3実装時に調整する)。
